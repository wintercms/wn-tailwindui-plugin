# Colour token tooling

Rebuilt 2026-09-14 after the original scratchpad was cleared. These live in git
precisely because the first set did not.

Everything assumes you run from the **Winter core root** (the directory with
`artisan/` and `modules/`), or that `WINTER_ROOT` is set.

---

## The one thing to know

Every rewrite is `#hex` → `var(--wn-token, #hex)`. **The literal it replaced is
carried in the fallback.** That single property is the whole safety story:

- the change is exactly revertible (`unapply.php` reads the fallback back out),
- it can be re-applied freely,
- and if the token block ever goes missing, compiled output is the original
  colours rather than nothing.

---

## Changing a colour

The common case. Edit the value in `tokens-values.json`, then:

```bash
php plugins/winter/tailwindui/darkmode-audit/tools/apply.php     # regenerates tokens.less
plugins/winter/tailwindui/darkmode-audit/tools/build.sh          # compiles both pipelines
php plugins/winter/tailwindui/darkmode-audit/tools/verify.php    # nothing unintended repainted?
php plugins/winter/tailwindui/darkmode-audit/tools/contrast.php  # did contrast move?
```

`tokens.less` is **generated** — edit `tokens-values.json`, not the `.less`.

## Scripts

| script | what it does |
|---|---|
| `apply.php` | replays `token-map.json` onto the source and regenerates `tokens.less`. Idempotent. |
| `unapply.php` | reverts every rewrite, deletes `tokens.less`, removes its import. `--dry` to preview. |
| `build.sh` | compiles **both** pipelines with plugins disabled, restores their prior state. |
| `verify.php` | proves no selector paints a different colour set than pristine. `--capture` to (re)make baselines. |
| `contrast.php` | WCAG 2.1 before/after on pairs that genuinely co-occur. Exits non-zero if anything newly fails AA. |
| `extract-map.php` | re-captures `token-map.json` from the applied tree. Run after hand-editing a token reference. |
| `lab.php` | CIELAB / ΔE / chroma / WCAG helpers. |

## Data

| file | what it is |
|---|---|
| `token-map.json` | the authoritative list of 657 rewrites (file, line, token, original hex) |
| `tokens-values.json` | the 165 token values, grouped; **this is the palette** |
| `baseline/*.css` | pristine compiled CSS for `verify.php` |

`token-map.json` was captured *from the applied tree* rather than regenerated by
re-running the original role-inference heuristics. Those heuristics were tuned
interactively and are not reproducible; the result of that tuning was already in
the tree, and reading it back cannot drift from what was built and reviewed.

## Traps that have cost real time here

**There are two build pipelines.** `winter.css` comes from `winter:util compile
less`; `storm.css` comes from mix. `storm.less` is *not* imported by
`winter.less`, and `tokens.less` is imported by `storm.less` — so the `:root`
block only ships in `storm.css`. Run both; `build.sh` does.

**`winter:util compile less` aborts the whole run on the first plugin whose LESS
fails**, quietly enough to look successful. `Winter.Builder`'s
`buildingarea.less` calls `.clearfix()` with no import and does not compile
against this core (pre-existing — reproduces on pristine core). `winter.css`
then silently stays stale. `build.sh` disables plugins for the compile and
greps the output for real errors.

**Never derive the root from `__DIR__` / `BASH_SOURCE`.** This directory is
normally reached via `plugins/winter/tailwindui` → `plugins-src/Winter/TailwindUI`,
and `plugins-src` is the *same directory* as the sibling `Plugins/` checkout, so
`realpath()` walks out of the core tree entirely. `coreRoot()` searches for
`artisan` + `modules/system/assets/ui/storm.less` instead.

**Re-capture baselines after `composer update`.** It overwrites `modules/` with
newer code than git HEAD, and stale baselines make upstream edits look like
token regressions.

**Token names contain digits** (`--wn-blockquote-level1-color`). A regex of
`--wn-[a-z-]+` silently skips them and breaks the round-trip. Always
`--wn-[a-z0-9-]+`.

**A `var()` fallback does NOT rescue a defined-but-invalid value.** If a token
is *defined* as something the browser cannot parse (e.g. `color-mix()` on an old
engine), `var(--token, #hex)` does **not** fall back — the declaration is invalid
at computed-value time and the element paints *transparent*. The usual
"static declaration first, `var()` second" trick does not help either, for the
same reason. Both verified in-browser.

So a token that needs a feature guard must be defined **inside** `@supports`, and
never unguarded. Where the guard fails the token stays *undefined*, which is the
one case `var()`'s fallback does handle. `tokens-values.json` supports a
`supports` key for this; `apply.php` emits those in a separate guarded block.

**A green build proves nothing about colour.** Every catastrophic misrouting
found in this work compiled cleanly — a red file icon turned white, `#fff`
turned dark navy, and the list zebra stripe turned white and vanished. Use
`verify.php` and `contrast.php`, and look at the UI.
